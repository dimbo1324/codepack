P-1. [ВЫСОКО] Внешний форматтер запускается без таймаута, и схема работы с его
     трубами допускает вечную взаимную блокировку
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `codepack-sanitize` отдаёт исходник внешнему форматтеру через stdin и читает
  результат из stdout:

      let mut child = Command::new(binary_path)
          .args(args).stdin(piped()).stdout(piped()).stderr(null()).spawn().ok()?;
      {
          let mut stdin = child.stdin.take()?;
          stdin.write_all(source.as_bytes()).ok()?;      // (1) пишем всё
      }
      let output = child.wait_with_output().ok()?;        // (2) потом читаем всё

  Два независимых дефекта.

  **(а) Взаимная блокировка труб.** Комментарий рядом объясняет, почему stdin
  закрывается до чтения:

      // every formatter here waits for EOF on stdin before it writes anything
      // back, and an open write end would deadlock the pipe.

  Вывод верный, а посылка — предположение о поведении **чужих программ**. Труба
  ОС имеет буфер (обычно 64 КиБ на Linux, схожий порядок на Windows). Если
  форматтер начинает писать в stdout раньше, чем дочитал stdin, — а так делают
  все потоковые фильтры, — то при исходнике больше буфера получается классика:
  дочерний процесс блокируется на записи в заполненный stdout, родитель
  блокируется на записи в заполненный stdin, и оба ждут друг друга **вечно**.

  Проверить, что ни `rustfmt`, ни `gofmt`, ни `ruff`, ни `black`, ни `clang-format`
  никогда так себя не ведут ни в одной версии, невозможно; а список кандидатов
  открытый — что окажется на `PATH` у пользователя, проект не решает.

  **(б) Нет таймаута и нет отмены.** `wait_with_output()` ждёт столько, сколько
  нужно. Форматтер, который завис по любой причине — ждёт блокировку, ждёт
  сеть (некоторые форматтеры лезут за конфигурацией), просто сломан, — вешает
  поток навсегда. Токен отмены в этот момент не смотрится: цикл по файлам
  проверяет отмену между файлами, а внутри `run_stdin` её нет. Значит,
  «Отмена» в интерфейсе на зависшем файле не сработает, а закрытие окна
  оставит поток жить.

  Ситуацию усугубляет `rayon`: `run/mod.rs` обрабатывает файлы параллельно, то
  есть зависнуть может сразу столько потоков, сколько ядер, и они займут весь
  пул rayon — включая тот, который используют другие части процесса.

К ЧЕМУ ПРИВОДИТ
  «Стерильная копия» зависает намертво, без сообщения, без возможности отменить,
  на файле, размер которого превысил буфер трубы. В десктопном приложении это
  выглядит как зависшая программа.

КАК ИСПРАВИТЬ (senior+)
  Оба дефекта закрываются одной перестройкой, и она стандартная.

  1. **Писать stdin в отдельном потоке, читать stdout в текущем.** Тогда обе
     трубы обслуживаются одновременно и блокировки не возникает при любом
     поведении дочернего процесса:

        let mut stdin = child.stdin.take()?;
        let source = source.to_owned();
        let writer = std::thread::spawn(move || {
            let _ = stdin.write_all(source.as_bytes());
            // drop(stdin) закрывает трубу — это и есть EOF, которого он ждёт
        });
        let output = child.wait_with_output().ok()?;
        let _ = writer.join();

     Это не «на всякий случай»: это единственная схема, корректная без
     предположений о чужой программе.

  2. **Таймаут.** `std::process::Child` не умеет ждать с ограничением, поэтому
     либо `wait-timeout` (крошечный крейт, ровно одна функция — оправдан по
     правилу «не тащить тяжёлую библиотеку ради одной функции»), либо
     собственный поток-сторож, который через N секунд делает `child.kill()`.
     N порядка 30 секунд на файл: форматтеру этого хватает с огромным запасом,
     а зависание становится ошибкой вместо вечности.

  3. **Отмена.** Тот же сторож проверяет токен раз в 100 мс и убивает процесс
     при отмене. Тогда «Отмена» работает и на зависшем файле, а не только между
     файлами.

  4. Тесты — №7 из списка в `04-TESTS.txt`: зависший форматтер и форматтер,
     пишущий больше объёма трубы. Оба падают на текущем коде.

P-2. [ВЫСОКО] Файл читается в память целиком, без потолка, параллельно на всех
     ядрах — и в команде `scan` потолок снят принудительно
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Сканер секретов на каждый файл делает:

      let raw = fs::read(&absolute)?;       // весь файл в Vec<u8>

  перед этим проверив `max_bytes_per_file`, если он задан. Задан он далеко не
  всегда:

    - `Config::text_file_size_limit_enabled` по умолчанию **false**, то есть у
      обычного экспорта потолка нет;
    - `codepack scan` выставляет `text_file_size_limit_enabled: false`
      принудительно, и делает это правильно — команда отвечает на вопрос «есть
      ли секрет в проекте», а не «влезет ли файл в бандл»;
    - десктопная команда `scan_project` — то же самое.

  Файл считается кандидатом на чтение, если его расширение в текстовом наборе.
  В наборе — `.sql`, `.csv`, `.log`, `.json`, `.xml`, `.txt`. То есть дамп базы
  на пять гигабайт, лог-файл, экспорт таблицы — всё это будет прочитано целиком.

  А теперь параллелизм: `scan_project` работает через `par_iter`, то есть на
  машине с 16 ядрами одновременно читается до 16 файлов. Пиковая память —
  сумма шестнадцати самых больших файлов, которым не повезло попасть в одну
  волну. Ограничения нет ни на одном уровне.

  Дополнительно: `raw` затем декодируется, и на этом месте появляется вторая
  копия того же объёма в виде `String`.

  Сравнение внутри проекта: шаг текстового дампа этот вопрос решил и записал
  решение (`ABSOLUTE_MAX_TEXT_FILE_BYTES = 256 МиБ`, «это не настройка»). Сканер
  — нет. Это Q-3 со стороны качества; здесь — со стороны последствий.

К ЧЕМУ ПРИВОДИТ
  `codepack scan` — команда, которую ставят в pre-commit-хук и в CI, то есть
  запускают в окружениях с жёстким лимитом памяти. На репозитории с большим

КАК ИСПРАВИТЬ (senior+)
  1. Общий потолок в `codepack-core` (см. Q-3), который нельзя выключить
     настройкой.
  2. Поведение при превышении — **не пропуск**. Пропустить большой файл значит
     не заметить в нём секрет, а именно этого команда `scan` избегать и
     создана. Правильно: прочитать первые N мегабайт, просканировать их и
     отметить файл в отчёте как просканированный частично, с указанием, сколько
     прочитано. Проект уже умеет так говорить — `history_scan` сообщает
     «walk truncated» и «blob skipped», и по тому же образцу.
  3. Ещё лучше — не читать целиком вовсе. Детектор работает построчно; чтение
     через `BufReader::lines()` с потолком на длину строки убирает пиковую
     память до размера одной строки. Это большая переделка (кэш сканирования
     ключуется по содержимому файла и требует всех байтов для хеша), поэтому
     как отдельная задача — но она снимает проблему целиком, а не смягчает.
  4. Ограничить и параллелизм по объёму: rayon умеет `ThreadPoolBuilder`, но
     проще ввести семафор по суммарному числу читаемых байтов. Это второй
     контур, и он нужен, только если решено оставить чтение целиком.
  5. Тест — №10 из списка в `04-TESTS.txt`, тяжёлый, рядом с `perf_smoke`.

P-3. [СРЕДНЕ] Гонка при первом открытии базы закрыта правильно; осталась одна
     тихая деградация
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Это разбор уже исправленного, и он здесь по двум причинам: подтвердить, что
  исправление верное (владелец прислал этот красный CI), и назвать остаток.

  Что было (прогон #106, обе ОС, разные таблицы — «table schema_version already
  exists» на Ubuntu, «table file_scan_cache already exists» на Windows):
  `migrate` читал версию схемы вне транзакции, а `Connection::transaction` в
  rusqlite — DEFERRED, то есть берёт блокировку записи на первой записи, а не
  в начале. Два соединения, открывающие новую базу, оба читали версию 0, оба
  выполняли `CREATE TABLE`, и проигравший падал.

  Разбор в сообщении коммита d406184 — образцовый: замечено, что «разные
  таблицы на разных ОС» означает не платформенное различие, а гонку.

  Что стало: версия читается **внутри** `TransactionBehavior::Immediate`, то
  есть второе соединение ждёт на взятии блокировки и потом видит
  зафиксированное первым. Дешёвое чтение без блокировки перед циклом сохраняет
  быстрый путь для уже мигрированной базы. Вторая гонка, вскрывшаяся под
  первой, — `PRAGMA journal_mode = WAL` не проходит через busy-handler, поэтому
  `busy_timeout` его не покрывал, — закрыта повторным чтением режима и
  ожиданием, а `busy_timeout` теперь ставится первым. Всё это верно.

  **Остаток.** `enable_wal` после 50 попыток по 20 мс сдаётся молча и
  возвращает `Ok(())`, оставив базу в rollback-режиме:

      // Every attempt was busy and the mode never became WAL. Journalling still
      // works … so this is not worth refusing to open for

  Решение защитимое. Но WAL — это не деталь: именно он позволяет читать во
  время записи, и на нём держится сценарий «приложение и CLI одновременно», ради
  которого гонку и чинили. В rollback-режиме читатель блокирует писателя, и
  симптом — «интерфейс подвисает во время экспорта» — не соотносится ни с чем
  наблюдаемым.

  Второй остаток, поменьше: секунда ожидания на открытии. При каждом открытии
  базы в контенденции это до 50 системных вызовов и сон, а `open_database()`
  в десктопе вызывается на каждую команду, а не один раз на процесс.

P-5. [СРЕДНЕ] Кэш сканирования: глобальный мьютекс на каждый файл и тихая
     потеря записей при отравлении
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `SqliteScanCache` — правильное решение непростой задачи: `rusqlite::Connection`
  не `Sync`, поэтому таблица читается в память до параллельного прохода, а
  всё новое буферизуется и пишется после. Рассуждение записано в заголовке
  модуля и оно верное.

  Две детали.

  **(а) Контенденция.** `lookup` на каждое попадание берёт глобальный мьютекс,
  чтобы отметить ключ использованным; `store` берёт другой глобальный мьютекс,
  чтобы добавить запись. То есть на каждый файл — минимум одно взятие
  разделяемой блокировки со всех потоков rayon. При 50 000 файлов это 50 000
  точек сериализации. Не катастрофа (критическая секция — вставка в
  `HashSet`), но это ровно та форма, которая перестаёт масштабироваться на
  машинах с большим числом ядер: чем больше потоков, тем хуже.

  **(б) Асимметрия при отравлении.** `flush` восстанавливается из отравления
  явно и с обоснованием:

      fn into_inner<T>(lock: Mutex<T>) -> T {
          lock.into_inner().unwrap_or_else(|error| error.into_inner())
      }

  А `lookup` и `store` — нет:

      if let Ok(mut used) = self.used.lock() { used.insert(…) }
      if let Ok(mut pending) = self.pending.lock() { pending.push(…) }

  После первой же паники в любом потоке rayon оба мьютекса отравлены навсегда,
  и весь остаток прохода кэш **молча перестаёт что-либо записывать и что-либо
  помечать использованным**. Следствие второго порядка: `prune_scan_cache`
  удалит записи, которые на самом деле использовались, потому что они не были
  помечены, — то есть кэш не просто не пополнится, он ещё и потеряет годное.

  Разница между `into_inner` и `lock()` здесь выглядит недосмотром, а не
  решением: рассуждение «кэш — оптимизация, отравление не должно ронять
  экспорт» записано ровно один раз и применено ровно в одном из трёх мест.

--------------------------------------------------------------------------------
P-6. [СРЕДНЕ] Два экспорта одного проекта могут идти одновременно, и ничто
     этому не мешает
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `RunRegistry::start()` заводит новый прогон всегда: ни проверки, что этот
  проект уже экспортируется, ни ограничения на общее число прогонов. Каждый
  `start_export` порождает поток, поток открывает своё соединение к базе, свою
  staging-директорию и свой набор отчётов.

  Что при этом может совпасть:
    - **Каталог вывода.** `build_export_paths` умеет разрешать коллизию имён
      счётчиком, и это проверено тестом
      (`build_export_paths_keeps_incrementing_past_multiple_collisions`). Но
      разрешение построено на «проверить, что каталога нет, и создать» — то есть
      само по себе TOCTOU. Два прогона, стартовавшие в одну секунду, могут
      выбрать одно имя.
    - **Базлайн снапшота.** Оба прогона в конце записывают снапшот источника.
      Кто последний, того и базлайн; при этом первый мог экспортировать другое
      состояние дерева. Дифференциальный экспорт после этого отвечает
      относительно того состояния, которое победило в гонке.
    - **Кэш сканирования.** Оба читают таблицу в память в начале и пишут в
      конце. Записи второго затирают статистику использования первого; `prune`
      может удалить то, что первый только что положил.

  Интерфейс, вероятно, не даёт нажать «Экспорт» дважды — но это утверждение о
  сегодняшнем UI, а не о границе. Ровно тот аргумент, который сам же этот
  модуль приводит про пути от вебвью: «„only ever“ is a statement about today's
  UI, not about the boundary».

ФАЙЛЫ
  apps/desktop/src-tauri/src/state.rs:55-70            (`start`, без проверок)
  apps/desktop/src-tauri/src/commands/export/mod.rs:41-52
  crates/codepack-engine/src/paths.rs                  (разрешение коллизии имён)

КАК ИСПРАВИТЬ (senior+)
  Не запрещать параллельные экспорты вообще — разные проекты параллельно
  экспортировать законно. Запретить **второй прогон того же проекта**:
  `RunRegistry` хранит множество активных корней, `start` возвращает
  `Err("этот проект уже экспортируется")`, если корень занят. Пять строк и
  один тест.

  Отдельно: создание каталога вывода — через `create_dir` (а не
  `create_dir_all`) в цикле подбора имени, потому что `create_dir` атомарно
  падает при существующем каталоге и тем самым разрешает гонку сам, без
  проверки «существует ли».


--------------------------------------------------------------------------------
P-7. [СРЕДНЕ] MCP-сервер обрабатывает один запрос за раз и не поддерживает
     отмену
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Записано в `overview.md` как известный долг, и формулировка честная:

      The MCP server handles one request at a time and does not implement
      cancellation: a tool call blocks the loop until it finishes, so a large
      export cannot be interrupted from the client.

  Аудит подтверждает и добавляет следствие, которого в формулировке нет. MCP —
  это поверхность для **агента**, а агент запускает `export` на чужом проекте
  без представления о его размере. Экспорт 50 000 файлов — четыре минуты по
  собственному замеру проекта. Всё это время сервер не отвечает даже на
  `initialize`, а протокольная отмена (`notifications/cancelled`) разбирается —
  в коде есть `a_cancellation_matches_only_the_request_it_names` и
  `a_late_cancellation_is_answered_with_silence` — но не приводит к остановке
  работы, потому что работа идёт в том же потоке, что и цикл чтения.

  То есть частичная реализация отмены хуже полного отсутствия: клиент шлёт
  отмену, получает подтверждение молчанием и продолжает ждать четыре минуты.

ФАЙЛЫ
  crates/codepack-cli/src/mcp/mod.rs
  docs/architecture/overview.md  (раздел Known debt)

КАК ИСПРАВИТЬ (senior+)
  Инфраструктура уже почти вся есть: `CancellationToken` пронизывает конвейер,
  а цикл MCP уже умеет опрашивать входящие строки во время работы (тесты
  `messages_arriving_during_a_call_are_answered_in_order`,
  `polled_lines_keep_their_arrival_order`). Не хватает одного: выполнять
  инструмент на отдельном потоке, держа его токен в карте по `request id`,
  и по `notifications/cancelled` дёргать токен. Это тот же приём, что уже
  реализован в десктопе (`RunRegistry`), и его стоит переиспользовать, а не
  писать заново.


--------------------------------------------------------------------------------
P-8. [СРЕДНЕ] Успешный прогон снимает снапшот исходного дерева дважды
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Записано в заголовке оркестратора, честно и с обоснованием:

      A successful run re-snapshots the **source** tree from scratch … even
      though step 1 may already have snapshotted the same tree once … Legacy's
      own `history_snapshot_payload` does exactly this … Caching or reusing
      step 1's snapshot here would be an undisclosed behavior change.

  Позиция «сначала паритет, потом улучшения» — правило проекта, и решение ей
  соответствует. Аудит не спорит; он называет цену, потому что в разделе про
  производительность её надо знать.

  Снапшот — это полный обход дерева плюс SHA-256 каждого файла. Хеширование
  потоковое (проверено), но это всё равно чтение всего проекта целиком второй
  раз. Для проекта на гигабайт — гигабайт лишнего ввода-вывода на каждый
  успешный экспорт, в режиме `--diff last-export` (а в других режимах шаг 1
  снапшот не делает, и тогда двойной работы нет).

КАК ИСПРАВИТЬ (senior+)
  Ничего не менять без решения владельца — это ровно тот случай, для которого
  правило «reproduce the wasteful legacy behavior rather than silently optimize
  it» и написано.

  Что стоит сделать: измерить и записать. Когда `perf_smoke` будет разложен по
  шагам (T-3, Q-7), цифра станет известной, и решение «оставить ради паритета»
  будет приниматься с ней на руках, а не в общем виде. Если окажется, что это
  20 % времени экспорта, разговор будет другим.


--------------------------------------------------------------------------------
P-9. [НИЗКО] Сортировки аллоцируют строку на каждое сравнение
--------------------------------------------------------------------------------

  Разобрано в Q-9. Здесь — только цифра: `sort_by` с `to_lowercase()` внутри
  компаратора при 50 000 элементов делает порядка 1,5 миллиона временных
  аллокаций. Лечится заменой на `sort_by_cached_key` (стабильность
  сохраняется, что важно для инварианта I5).


--------------------------------------------------------------------------------
P-10. [НИЗКО] Отчёты проверяют отмену между отчётами, а не внутри
--------------------------------------------------------------------------------

  Записано в `overview.md` как принятый долг: «`codepack-reports` checks
  cancellation between reports, not inside each report's file loop. Accepted
  deliberately: the pipeline level already bounds the risk.»

  Подтверждаю и добавляю одно уточнение: граница риска — это самый долгий
  отдельный отчёт. Кандидаты — `code_metrics` (читает каждый исходный файл и
  считает строки), `dependency_graph` (разбирает импорты во всех файлах) и
  `todo_fixme`. На проекте в 50 000 файлов каждый из них — десятки секунд,
  в течение которых «Отмена» не отвечает. Это стоит либо измерить и записать
  цифру рядом с принятым долгом, либо добавить проверку в три упомянутых цикла:
  три строки, ноль риска.


--------------------------------------------------------------------------------
P-11. [НИЗКО] Упаковка одного очень большого файла неотменяема
--------------------------------------------------------------------------------

  Тоже записанный долг. Отмена проверяется между членами архива; `io::copy`
  одного члена идёт до конца. Для файла в несколько гигабайт это минуты.

  Лечится потоковым копированием кусками с проверкой токена между кусками —
  `io::copy` заменяется на цикл по буферу в 64 КиБ. Десять строк, и они же
  дают возможность сообщать прогресс внутри большого файла, чего сейчас нет.

ЧТО ПРОВЕРЕНО ПО ПАРАЛЛЕЛИЗМУ И ОКАЗАЛОСЬ В ПОРЯДКЕ
================================================================================

  - **Гонок данных нет.** Всё разделяемое состояние — под `Mutex`; `unsafe`
    отсутствует; `Send`/`Sync` нигде не реализуются вручную.
  - **Отравление мьютексов обработано осознанно** в трёх местах из четырёх,
    с записанным рассуждением, почему для этих конкретных данных восстановление
    корректно, а не с ритуальным `.expect("never poisoned")`. Четвёртое —
    P-5(б).
  - **Параллельный скан не меняет вывод ни на байт**, и это доказано
    конструкцией, а не надеждой: `par_iter` индексирован, `collect`
    восстанавливает входной порядок, сортировки стабильны, а первая ошибка
    выбирается по входному порядку, а не по тому, какой поток упал раньше.
    Рассуждение записано в заголовке `scan/mod.rs` — это один из лучших
    комментариев в кодовой базе.
  - **Отмена проверяется внутри циклов**, а не только между шагами: в обходе
    сканера, в снапшоте, в копировании, в текстовом дампе, в упаковке, в
    per-file цикле sanitize. Восемь тестов на границы отмены.
  - **RAII-очистка staging** срабатывает на всех путях выхода, включая ранний
    возврат через `?` и панику; на это есть отдельный тест.
  - **Каскад отмены** воспроизведён из legacy сознательно, с разбором того,
    какие шаги выполняются всегда и почему, и с отдельным различением
    «защёлкнутого» флага и свежей перепроверки токена.
  - **Debounce наблюдателя** переписан с leading-edge на trailing-edge, и тесты
    описывают поведение («всплеск даёт одно уведомление со всеми путями»,
    «последнее изменение серии не теряется», «два разделённых всплеска — два
    уведомления»), а не реализацию.
  - **Поток агрегатора привязан к владению наблюдателем** одним значением, и
    `Drop` его джойнит, а не отсоединяет, — с объяснением, что поток,
    держащий `AppHandle` после закрытия окна, превращает завершение в зависание.
  - **Канал прогресса неблокирующий**: каждая отправка — `let _ = …`, и
    контракт «рабочий поток никогда не блокируется» записан.
  - **Хеширование снапшота потоковое**, кусками по 1 МиБ, с тестом на границы
    кусков.
  - **WAL и `busy_timeout`** применяются на каждое соединение, и объяснено,
    почему это не может быть частью SQL-миграции.
