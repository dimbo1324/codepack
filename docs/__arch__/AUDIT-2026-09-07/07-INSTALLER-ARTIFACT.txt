РАЗДЕЛ D. ДУБЛЬ УСТАНОВЩИКА В КОРНЕ РЕПОЗИТОРИЯ
================================================================================

Дата: 2026-09-07. Ветка main, коммит 8d747ed (2026-09-06T22:20:47+03:00).

Требование владельца, дословно по смыслу: при компиляции получается `.exe`,
которым программа устанавливается. Пусть этот файл остаётся там, где он сейчас,
но дополнительно создаётся его дубликат с понятным пользователю именем
(например `setup`), кладётся в корень проекта, учитывается в системе контроля
версий и упоминается в документации — чтобы человек мог увидеть его на GitHub и
скачать, не разыскивая по каталогам.

Раздел устроен так: сначала состояние, потом одно возражение по существу
(коротко, как и положено), потом полное решение именно той задачи, которая
поставлена, потом — что делать с тем, о чём возражение.


--------------------------------------------------------------------------------
СОСТОЯНИЕ
--------------------------------------------------------------------------------

  `cargo xtask package` (он же скрипт `build-installer`) запускает `tauri build`
  и затем перечисляет всё, что бундлер произвёл, по каталогам форматов:

      target/release/bundle/nsis/codepack_2.0.0_x64-setup.exe
      target/release/bundle/nsis/SHA256SUMS.txt
      target/release/bundle/deb/codepack_2.0.0_amd64.deb
      target/release/bundle/deb/SHA256SUMS.txt
      target/release/bundle/rpm/…
      target/release/bundle/appimage/…

  Никуда, кроме `target/`, ничего не копируется. `target/` в `.gitignore`, так
  что установщика в репозитории нет и никогда не было.

  Канала доставки тоже нет: GitHub Releases не используется, workflow для
  релиза нет, README предлагает собрать установщик самому. То есть сегодня
  человек, желающий поставить codepack, должен установить Rust, Node, pnpm и
  системные библиотеки Tauri — то есть быть разработчиком. Требование владельца
  метит ровно в это, и метит верно: у продукта нет способа его получить.


--------------------------------------------------------------------------------
ВОЗРАЖЕНИЕ ПО СУЩЕСТВУ, ОДИН АБЗАЦ
--------------------------------------------------------------------------------

  Бинарный файл в git необратим: он остаётся в истории навсегда, и каждый, кто
  клонирует репозиторий, скачивает все его версии, а не последнюю. При размере
  установщика порядка 10–20 МБ и, скажем, десяти релизах в год репозиторий
  прибавляет 100–200 МБ в год, и убрать это можно только переписыванием
  истории. GitHub предупреждает на файлах больше 50 МБ и отказывает на 100 МБ.
  Штатный механизм для этой задачи — GitHub Releases: файл виден на странице,
  скачивается одним нажатием, не попадает в клон и имеет счётчик загрузок.
  Второй довод сильнее первого: README этого проекта прямо аргументирует против
  скачивания неподписанных бинарей («downloading an unsigned one would be the
  very thing this tool argues against»), а файл в корне репозитория — это
  именно такой канал, только без даты, без журнала и без возможности отозвать.

  Возражение высказано, дальше — решение той задачи, которая поставлена. Раздел
  «ЕСЛИ ПОТОМ ЗАХОЧЕТСЯ ИНАЧЕ» в конце показывает, как это же решение
  превращается в Releases без переделки.


--------------------------------------------------------------------------------
D-1. РЕШЕНИЕ: `setup.exe` В КОРНЕ, ПОД КОНТРОЛЕМ ВЕРСИЙ
--------------------------------------------------------------------------------

**Что появляется в корне**

      setup.exe            дубликат NSIS-установщика, имя постоянное
      SETUP.txt            что это за файл: версия, дата, хеш, коммит

  Два файла, а не один, и второй важнее, чем кажется. Постоянное имя `setup.exe`
  — это то, о чём просил владелец, и оно правильно для ссылки из README: ссылка
  не должна меняться от релиза к релизу. Но у постоянного имени есть цена:
  **по файлу нельзя сказать, какая это версия**. Человек, скачавший `setup.exe`
  полгода назад, не отличит его от сегодняшнего. `SETUP.txt` эту цену снимает:

      codepack setup
      ────────────────────────────────────────────────────────
      файл:      setup.exe
      версия:    2.0.0
      платформа: Windows x64 (NSIS, установка для текущего пользователя)
      собран:    2026-09-07T01:14:32+03:00
      коммит:    8d747ed
      источник:  target/release/bundle/nsis/codepack_2.0.0_x64-setup.exe
      sha256:    3f1a…c07b

      Проверить перед запуском (PowerShell):
          Get-FileHash .\setup.exe -Algorithm SHA256

      Установщик не подписан: SmartScreen предупредит о неизвестном издателе.
      Подпись — этап S14.

  Формат — тот же, что уже принят в проекте для `SHA256SUMS.txt`: человекочитаемо,
  без инструментов. Полный момент с зоной — по правилу
  `09-time-and-timestamps.md`.

**Где это делается: в `xtask`, не в скрипте**

  `cargo xtask package` и `python dev_tools_scripts_runner.py build-installer` —
  две двери к одной работе, и скрипт по устройству проекта только оборачивает
  xtask, а не повторяет его. Значит, копирование делает `xtask`, и обе двери
  получают его бесплатно. Место — `frontend::report_bundles`, которая уже
  обходит каталоги форматов и уже считает SHA-256.

  Набросок:

      /// Кладёт рядом с репозиторием дубликат установщика под постоянным именем.
      ///
      /// Имя постоянное — на него ссылается README, и ссылка не должна меняться
      /// от релиза к релизу. Поэтому рядом пишется `SETUP.txt`: по самому файлу
      /// версию не узнать, а знать её надо и тому, кто скачал, и тому, кто
      /// проверяет, что дубликат не отстал от сборки.
      ///
      /// Только основной формат платформы. Класть в корень все четыре
      /// (deb/rpm/AppImage/exe) значило бы держать в git четыре бинаря вместо
      /// одного ради удобства, которое даёт один.
      fn publish_root_installer(root: &Path, produced: &[PathBuf]) -> Result<(), String>

  Выбор основного формата — таблицей, а не условием, чтобы это было данными:

      Windows → nsis/*-setup.exe        → setup.exe
      Linux   → appimage/*.AppImage     → setup.AppImage   (см. ниже)
      macOS   → сборки нет

  AppImage выбран для Linux осознанно: он единственный из трёх форматов,
  который запускается без установки и без пакетного менеджера, то есть
  соответствует смыслу слова «setup» для человека, который просто хочет
  попробовать программу. Но: **владелец просил про `.exe`**, поэтому Linux-часть
  делать не обязательно, и её стоит согласовать отдельно — каждый файл в корне
  стоит места в истории.

**Как это не отстанет от сборки**

  Главный риск этого решения — не размер, а **устаревание**. `setup.exe` в
  корне будет обновляться руками, а значит, однажды не обновится, и
  пользователи будут скачивать прошлую версию, думая, что скачивают текущую.
  Это хуже, чем отсутствие файла.

  Защита — шаг гейта, ровно в том же жанре, что `sync-agents --check`
  («расхождение AGENTS.md с модулями ломает сборку намеренно»):

      === installer artifact ===
      setup.exe: версия 2.0.0 совпадает с Cargo.toml, sha256 совпадает с SETUP.txt

  Проверяются три вещи, все дешёвые и все без сборки установщика:
    1. `SETUP.txt` существует и разбирается;
    2. версия в нём совпадает с `workspace.package.version`;
    3. sha256 файла `setup.exe` совпадает с записанным в `SETUP.txt`.

  Третья ловит подмену и порчу; вторая — ровно ту ситуацию, ради которой всё
  это: версию подняли, установщик не пересобрали. Проверка не может убедиться,
  что `setup.exe` собран **из этого** коммита (для этого пришлось бы собирать
  установщик в гейте, а это десять минут), и это ограничение надо назвать в
  сообщении проверки честно — иначе оно создаст ложную уверенность.

  Полную гарантию даёт CI: джоба, которая на теге собирает установщик и
  сравнивает его хеш с закоммиченным. Она медленная, поэтому только на теге.

**Учёт в системе контроля версий**

  `.gitignore` менять не нужно: `*.exe` там не перечислен, `/target/` не
  затрагивает корень. `setup.exe` и `SETUP.txt` добавляются как обычные файлы.

  Что стоит добавить — атрибут, чтобы git не пытался считать файл текстовым и
  не показывал diff:

      # .gitattributes
      setup.exe binary
      setup.AppImage binary

  В `.gitattributes` уже есть записи такого рода, так что это одна строка в
  существующий файл.

**Чтобы установщик не попал в собственный экспорт**

  Деталь, которую легко пропустить и которая проявится сразу: codepack умеет
  экспортировать сам себя (и делает это в приёмочном шаге CI). `.exe` относится
  к бинарным расширениям, то есть в текстовый дамп не попадёт, но **в архив
  будет скопирован** — и каждый самоэкспорт станет на 10–20 МБ тяжелее без
  всякой пользы.

  Лечится строкой в `.exportignore` в корне (сейчас такого файла нет, он
  появится):

      # Дубликат установщика: бинарь, к исходникам отношения не имеет
      setup.exe
      setup.AppImage

  Это же служит живым примером формата `.exportignore` в собственном
  репозитории, чего сейчас нет.

**README**

  Раздел Install переписывается так, чтобы скачивание было первым, а сборка —
  вторым:

      ## Install

      **Windows.** Скачайте [setup.exe](setup.exe) (текущая версия и контрольная
      сумма — в [SETUP.txt](SETUP.txt)) и запустите. Установка идёт для текущего
      пользователя, права администратора не нужны.

      Проверьте файл перед запуском:
          Get-FileHash .\setup.exe -Algorithm SHA256
      и сверьте с `SETUP.txt`. Установщик не подписан — SmartScreen предупредит
      о неизвестном издателе; подпись запланирована (этап S14).

      **Linux.** … (после L-1: пакеты и CLI)

      **Из исходников.** cargo xtask package

  Ссылка `[setup.exe](setup.exe)` на GitHub ведёт на страницу файла с кнопкой
  Download — это лучше прямой ссылки на `raw`, потому что страница показывает
  размер, дату и историю, а `raw` отдаёт файл без всякого контекста. Прямую
  ссылку стоит дать рядом, для тех, кому нужна одна команда:

      https://github.com/dimbo1324/codepack/raw/main/setup.exe

  И обязательно — предупреждение про неподписанный бинарь. Оно уже есть в
  README применительно к сборке; здесь оно нужнее, потому что здесь файл
  предлагается скачать.

**Что сказать в документации проекта**

  Изменение затрагивает то, «что пользователь может скачать и запустить», а
  правило `13-progress-tracking.md` требует в этом случае обновить README (уже
  учтено) и, поскольку меняется процедура выпуска, — записать решение в
  `docs/__arch__/open-questions.md` как Q44: «дубликат установщика в корне
  репозитория, под контролем версий», с решением владельца, датой и той
  оговоркой про рост истории, которая высказана выше. Без записи следующая
  сессия увидит бинарь в корне и не поймёт, намеренно ли он там.


--------------------------------------------------------------------------------
D-2. ПОРЯДОК РАБОТ
--------------------------------------------------------------------------------

  1. `xtask`: `publish_root_installer` внутри `package`, таблица «платформа →
     формат → имя», запись `SETUP.txt`. Тесты — на выбор формата и на разбор
     `SETUP.txt`, без реальной сборки (как уже устроены тесты `write_checksums`).
  2. Шаг гейта `installer artifact`: три проверки выше. Быстрый, идёт и в
     `--quick`.
  3. `.gitattributes`: `setup.exe binary`.
  4. `.exportignore` в корне.
  5. README: раздел Install переписан, скачивание первым.
  6. `open-questions.md`: Q44 с решением и оговоркой.
  7. Первый коммит с самим `setup.exe` — отдельно от кода, с сообщением
     `release: setup.exe for 2.0.0`, чтобы бинарь не смешивался с изменениями
     логики в одном diff.


--------------------------------------------------------------------------------
D-3. ЕСЛИ ПОТОМ ЗАХОЧЕТСЯ ИНАЧЕ
--------------------------------------------------------------------------------

  Решение выше не закрывает дорогу ни к одному из вариантов, и это стоит знать
  заранее.

  **Git LFS.** Если рост истории станет заметен, `setup.exe` переводится в LFS
  одной строкой `.gitattributes` (`setup.exe filter=lfs diff=lfs merge=lfs -text`)
  плюс миграция истории. Ссылка из README продолжает работать, размер клона
  перестаёт расти. Минус: клонирующему нужен установленный `git-lfs`, а у
  GitHub есть квота на трафик LFS.

  **GitHub Releases.** Та же функция `publish_root_installer` в CI на теге
  загружает файл в релиз — `softprops/action-gh-release` или `gh release upload`.
  `setup.exe` в корне при этом можно оставить (он станет «последней стабильной»
  копией) или заменить на ссылку. Здесь же логично добавить
  `actions/attest-build-provenance`: аттестация происхождения доказывает, что
  файл собран этим workflow из этого коммита, — а это ровно то, чего не даёт
  контрольная сумма рядом с файлом, и то, что снимает половину возражения из
  начала раздела.

  **Подпись.** Ортогональна выбору канала. Сертификат для Windows — решение
  владельца и деньги; GPG для Linux-пакетов — бесплатно и делается за час
  (см. S-6). Ни то, ни другое не требует переделывать D-1.

  Рекомендуемая последовательность, если делать всё: D-1 сейчас (он решает
  задачу владельца), Releases с аттестацией следующим шагом (он снимает
  возражение), подпись — когда будет решение по сертификату.
