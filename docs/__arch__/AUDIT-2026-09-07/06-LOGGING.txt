================================================================================
G-1. ЖУРНАЛ РАБОТЫ ПРОГРАММЫ
================================================================================

--------------------------------------------------------------------------------
СОСТОЯНИЕ: журнала нет ни в каком виде
--------------------------------------------------------------------------------

  Проверено поиском по всему дереву:

    - Ни `tracing`, ни `log`, ни `env_logger`, ни `fern`, ни `simplelog` — ни в
      корневом `Cargo.toml`, ни в одном манифесте крейта. Логирующего фасада в
      проекте нет вовсе.
    - `AppPaths::log_dir()` **определён** для всех трёх платформ, покрыт тестом
      — и не вызывается ни разу. Ноль совпадений по всему дереву вне `paths.rs`
      (это Q-10).
    - Единственное, что похоже на журнал, — `ProgressEvent::Log(LogEvent)`:
      структура с уровнем и сообщением, отправляемая в канал. Её потребители:
        * CLI — печатает в stderr (`output::note`), и только;
        * десктоп — пересылает в вебвью как событие, интерфейс показывает
          последние строки;
        * MCP — не потребляет вовсе.
      Ни один потребитель ничего не сохраняет. Закрылось окно — журнала нет.
      Закончилась команда — журнала нет.

  Что это означает на практике. Экспорт на 50 000 файлов пишет по строке на
  файл: «copied: …», «skipped by safety mode: … (reason)», «cannot copy …: …».
  Это самая ценная диагностика, какая есть в продукте: она отвечает на вопрос
  «почему этого файла нет в бандле» пофайлово. И она уничтожается сразу после
  показа.

  Отдельно про аварии: `[profile.release] strip = "symbols"`. При панике
  пользователь не получит ни стека, ни имён функций, ни файла с сообщением —
  на Windows в release-сборке консоль скрыта (`windows_subsystem = "windows"`),
  то есть паника вообще нигде не видна. Приложение просто исчезает.

  Итого сегодня, если пользователь напишет «экспорт пропустил половину файлов»
  или «приложение закрылось само», ответить нечем.

--------------------------------------------------------------------------------
ЧТО ЭТО ЗА ЗАДАЧА НА САМОМ ДЕЛЕ: ТРИ ОГРАНИЧЕНИЯ, КОТОРЫЕ ЕЁ ФОРМИРУЮТ
--------------------------------------------------------------------------------

  Прежде чем выбирать библиотеку, надо назвать то, что в этом конкретном
  проекте делает журнал нетривиальным.

  **(1) Инвариант I3.** «Значение найденного секрета никогда не попадает в лог,
  отчёт, историю, базу, сообщение об ошибке или буфер обмена.» Лог там стоит
  первым словом. Значит, файл журнала — это артефакт, к которому I3 применяется
  напрямую, и сегодня повествование конвейера через редакцию **не проходит**
  (это S-8 в `02-SECURITY.txt`). Пока лога нет, это теоретическая проблема; в
  день, когда лог появится, она станет настоящей.

  **(2) Раскрытие путей машины.** Решение Q40 (2026-09-06) сделало
  `disclose_absolute_paths` выключенным по умолчанию: бандл больше не называет
  каталоги машины, на которой собран. Журнал по своей природе называет их
  постоянно. Это правильно — журнал для своей машины, — но как только
  пользователь приложит его к обращению, он отдаст ровно то, что бандл
  специально перестал отдавать. Значит, у журнала должно быть два режима, и по
  умолчанию — тот, который безопасен при пересылке. Или, как минимум, команда,
  которая готовит журнал к отправке.

  **(3) Объём.** Строка на файл — это на 50 000 файлов около 4–6 МБ на прогон.
  Без ротации каталог логов вырастет до гигабайтов за месяц активной работы.

--------------------------------------------------------------------------------
ПРЕДЛАГАЕМОЕ РЕШЕНИЕ
--------------------------------------------------------------------------------

**Куда писать**

  Использовать уже существующий `AppPaths::log_dir()`, предварительно исправив
  его (это L-6):

      Windows   %LOCALAPPDATA%\codepack\logs\
      macOS     ~/Library/Logs/codepack/
      Linux     $XDG_STATE_HOME/codepack/logs/   (по умолчанию ~/.local/state/…)

  Имя файла — `codepack-YYYY-MM-DD.log`, по дню. Не по прогону: прогонов может
  быть много, и «найти лог того запуска» тогда становится задачей. По дню —
  один файл, в нём все прогоны, разделённые заголовком с идентификатором
  прогона.

  Правило по времени, которое проект уже установил для себя
  (`09-time-and-timestamps.md`): **каждая строка несёт полный момент с зоной**.
  Не `14:23`, не «2 минуты назад», а `2026-09-06T22:20:47+03:00`. Это правило
  придумано ровно для того случая, когда в один день происходит несколько
  событий и надо их упорядочить, — то есть для лога.

**Формат строки**

      2026-09-06T22:20:47.318+03:00  INFO  run=r-7f3a  step=copy   copied: src/main.rs
      2026-09-06T22:20:47.402+03:00  WARN  run=r-7f3a  step=copy   skipped by safety mode: .env (sensitive filename)
      2026-09-06T22:20:49.001+03:00  ERROR run=r-7f3a  step=archive cannot write part 2: No space left on device

  Плоский текст, а не JSON: этот лог читает человек, и `grep` по нему должен
  работать без инструментов. Поле `run=` обязательно — без него два
  одновременных экспорта (P-6) перемешаются в одном файле нечитаемо.

  Стоит рассмотреть **второй, машинный** файл (`codepack-YYYY-MM-DD.jsonl`) для
  тех же событий — но только если появится потребитель. Писать оба «на всякий
  случай» — удвоить объём ради гипотезы.

**Ротация и срок хранения**

  Простая и достаточная политика, вся в конфигурации:
    - новый файл каждый день;
    - файл больше 50 МБ закрывается и продолжается как `.1`, `.2`, …;
    - файлы старше 14 дней удаляются при старте приложения;
    - суммарный потолок 200 МБ, при превышении удаляются самые старые.

  Все четыре числа — поля `Config` со `schema_version`, а не константы: это
  ровно те значения, которые у разных пользователей разные, и повод открывать
  код ради них — плохой повод. Значение `log_retention_days = 0` означает
  «не хранить вовсе», и это должно работать: пользователю, которому журнал не
  нужен, надо дать выключить его целиком.

**Уровни и что на каком**

    ERROR  то, что не получилось и о чём пользователю стоит знать
    WARN   пропуск с причиной: safe-mode, размер, кодировка, недоступный файл
    INFO   границы шагов, конфигурация прогона, итоговые числа
    DEBUG  строка на файл («copied: …») — по умолчанию **выключено**

  Это важное решение: сегодняшнее пофайловое повествование — это DEBUG, а не
  INFO. На уровне по умолчанию лог одного экспорта должен быть в районе сотни
  строк, а не пятидесяти тысяч. Включение — переменной окружения
  `CODEPACK_LOG=debug` и переключателем в настройках приложения.

**Редакция — не по договорённости, а по конструкции**

  Это самая важная часть, и она должна быть сделана до первой записи в файл,
  а не после.

  Не «не забывать вызывать `redact_secrets` при логировании». Проект этот урок
  уже проходил дважды: сначала с отчётами (появился гейт-шаг
  `report_redaction`), потом с ошибками (появился `RenderedError` с приватным
  полем). Здесь та же форма:

      /// Строка, прошедшая редакцию, и единственное, что умеет писать `LogSink`.
      /// Приватное поле: сконструировать иначе, чем через `of`, нельзя.
      pub struct LogLine(String);
      impl LogLine {
          pub fn of(message: &str) -> Self {
              Self(codepack_security::redact_secrets(message))
          }
      }

  и `LogSink::write(&self, line: LogLine)`. Тогда «кто-то записал в лог сырую
  строку» — не ошибка дисциплины, а несуществующая операция.

  Второй контур — тест на класс ошибки, а не на случай: прогнать экспорт
  проекта с подсаженным секретом и потребовать, чтобы значение секрета не
  встречалось в файле журнала. Близнец уже существующего
  `planted_secrets_never_reach_the_text_dump` (это тест №9 из списка в
  `04-TESTS.txt`).

  Здесь есть один тонкий момент, который стоит решить сознательно: узкая
  `redact_secrets` или широкая `redacted_line`. CLI выбрал узкую, и объяснил
  почему — широкая превращала собственную прозу продукта («pass --hook to
  install…») в `<REDACTED>`. Для журнала действует тот же довод: он состоит из
  прозы продукта и путей, а не из чужого исходного кода. Значит — узкая, и
  комментарий рядом со ссылкой на рассуждение в `main.rs`, чтобы следующий
  человек не «усилил» её.

**Пути машины и подготовка журнала к пересылке**

  По умолчанию журнал пишет настоящие пути: он на своей машине, и без путей он
  бесполезен. Для пересылки — отдельная команда:

      codepack doctor --collect-logs [--out codepack-logs.zip]

  которая собирает журналы за N дней, прогоняет их через ту же замену, что
  используется при `disclose_absolute_paths = false` (заменяя корень проекта и
  домашний каталог на имя проекта и `<HOME>`), и пакует в архив. Реализация
  почти вся уже есть: `ReportContext::disclosed_source_root` решает ту же
  задачу для отчётов, и правильно переиспользовать её, а не написать вторую.

**Что писать: три категории**

  1. **Границы и конфигурация прогона (INFO).** Что экспортируется, каким
     профилем, в каком safe-режиме, каким diff-режимом, с каким бюджетом; когда
     начался и закончился каждый из восьми шагов и сколько занял. Это то, что
     нужно в 90 % обращений, и это сотня строк.
  2. **Всё, что пропущено, с причиной (WARN).** Сегодня это существует и
     теряется. Именно это отвечает на «почему файла нет в бандле».
  3. **Аварии (ERROR) с достаточным контекстом.** Здесь надо решить вопрос про
     `strip = "symbols"`: без символов паника в release не даст ничего
     полезного. Варианты: `strip = "debuginfo"` вместо `"symbols"` (бинарь
     чуть больше, имена функций остаются), либо `split-debuginfo` с публикацией
     символов рядом с релизом. Второе правильнее, но требует канала доставки
     (см. S-6). Минимум, который надо сделать сразу, — установить
     `std::panic::set_hook`, который пишет сообщение паники и место в журнал
     **до** того, как процесс умрёт. Одно это превращает «приложение исчезло»
     в «приложение исчезло, и вот на какой строке».

**Библиотека**

  `tracing` + `tracing-subscriber` + `tracing-appender`. Обоснование по правилу
  «новая зависимость требует оправдания»:
    - фасад нужен в любом случае, писать свой — это тот самый случай, когда
      «не тащить библиотеку ради одной функции» не применяется: тут не одна
      функция, а фильтрация по уровням, форматирование, неблокирующая запись и
      ротация;
    - `tracing` даёт спаны, а у этого конвейера ровно спановая структура
      (прогон → шаг → файл), то есть поля `run=` и `step=` возьмутся из
      контекста, а не будут передаваться руками в каждый вызов;
    - `tracing-appender` даёт неблокирующую запись отдельным потоком — важно,
      потому что писать в файл из цикла копирования нельзя;
    - лицензия MIT, зависимостей мало, поддерживается.

  Альтернатива для минимализма — `log` + собственный `LogSink` на ~80 строк.
  Дешевле по зависимостям, дороже по коду, и спаны придётся эмулировать. Если
  владелец предпочтёт этот путь — он рабочий, но `run=`/`step=` тогда идут в
  сигнатуре, и это будет заметно в каждом вызове.

  Важное ограничение, которое **нельзя нарушить**: `tracing` добавляется в
  оболочки (`codepack-cli`, `codepack-desktop`) и, возможно, в `codepack-engine`
  — но не в доменные крейты, если это потребует им знать про подсистему вывода.
  Инвариант I8 («ядро не зависит от интерфейса») этого прямо не запрещает, но
  архитектура проекта построена на том, что доменные крейты сообщают о себе
  через `ProgressSender`, а не через глобальный логгер. Правильная форма:
  **сохранить существующий канал прогресса как единственный источник событий**
  и добавить ещё одного его потребителя — файловый sink. Тогда ни один
  доменный крейт не меняется вовсе, а лог получается ровно тот же, что видит
  интерфейс.

  Это, кстати, лучшая часть новости: канал уже есть, события уже структурированы
  (`Log`, `StepStarted`, `StepFinished`, `StepProgress`), и подписать на него
  файловый потребитель — это не переделка, а добавление.

  7. `codepack doctor --collect-logs`, использующий уже существующую замену
     путей.
  8. Раздел в README: где лежат логи на каждой платформе, как включить DEBUG,
     как собрать для отправки. Без этого пункта функция наполовину не сделана.

G-2. ОТЧЁТ О ПРОГОНЕ ТЕСТОВ И ГЕЙТА
================================================================================

--------------------------------------------------------------------------------
СОСТОЯНИЕ
--------------------------------------------------------------------------------

  `cargo xtask gate` — десять секций. Девять из них пишут прямо в консоль и
  ничего не сохраняют. Одна, `tests`, **захватывает** вывод cargo (это сделано
  специально) и печатает его целиком, а под CI дополнительно превращает каждый
  упавший тест в аннотацию workflow с текстом паники.

  Это очень хорошая работа, и рассуждение к ней записано: лог шага в GitHub
  Actions требует прав администратора на репозиторий, а аннотация — нет, и
  именно этот разрыв полгода держал Q21 нераскрытым.

  Чего нет:
    - файла с результатом. Прогон закончился — в консоли текст, который
      прокрутился;
    - машинного формата (JUnit XML или JSON), который умеет читать любой
      CI-интерфейс;
    - времени: сколько заняла каждая секция и какие тесты самые медленные;
    - истории: сравнить сегодняшний прогон со вчерашним нечем.

--------------------------------------------------------------------------------
ПРЕДЛАГАЕМОЕ РЕШЕНИЕ
--------------------------------------------------------------------------------

**Куда**

      target/gate-logs/<YYYY-MM-DDTHH-MM-SS>/
          00-summary.txt          какие секции, сколько заняли, что упало
          01-format.log
          02-format-ai-api.log
          03-clippy.log
          04-tests.log            полный вывод cargo test
          04-tests.junit.xml      машинный формат
          05-deny.log
          …
          latest -> …             симлинк/копия на последний прогон

  `target/` — потому что это артефакт сборки, он уже в `.gitignore`, и его
  чистит `cargo clean` и `clean-project`. Класть отчёты о прогоне в корень
  репозитория было бы ошибкой: они мусорят рабочее дерево и попадут в
  собственный экспорт проекта.

  `latest` — потому что «где отчёт от последнего прогона» не должно требовать
  сортировки каталогов по имени.

**Как получить машинный формат**

  У `cargo test` его нет в стабильном виде (`--format json` требует nightly).
  Два честных пути:

  (а) **`cargo nextest`** — умеет `--profile ci` с JUnit XML из коробки, плюс
      параллельное выполнение по процессам (что, к слову, само по себе
      подсветило бы T-2: тесты, дерущиеся за общее состояние, там падают
      надёжнее). Цена — ещё один инструмент в требованиях к среде, и его надо
      будет ставить в CI и упоминать в `doctor`.

  (б) **Разобрать вывод `cargo test` самим.** Xtask это уже делает: функции
      `failed_test_names` и `failure_details` разбирают блок `failures:` и
      секции `---- name stdout ----`. Расширить их до полного результата
      (имя, статус, время из строки `test result:`) и выписать JUnit XML —
      это порядка ста строк и ноль новых зависимостей.

  Рекомендация: начать с (б). Разбор уже написан наполовину, а введение
  nextest — отдельное решение, которое стоит принимать не ради XML.

**Что в сводке**

      gate 2026-09-06T22:20:47+03:00   репозиторий: 8d747ed (main, чисто)
      ──────────────────────────────────────────────────────────────────
        format               ok        3.1s
        format (ai-api)      ok        0.4s
        clippy               ok       41.7s
        tests                FAILED   62.3s   1 из 1600 упал
            paths::tests::db_file_lives_under_the_data_dir
        deny                 ok        8.9s
        …
      ──────────────────────────────────────────────────────────────────
      итог: FAILED (секция tests), суммарно 2м 41с

  Полный момент с зоной — по тому же правилу
  (`09-time-and-timestamps.md`). Хеш коммита и чистота дерева — потому что
  «на чём именно был прогон» это первый вопрос при разборе.

**Тот же отчёт в CI**

  Аннотации остаются — они решают задачу, которую файл не решает (видимость без
  прав администратора). Добавляется:
    - `00-summary.txt` дописывается в `$GITHUB_STEP_SUMMARY`: тогда сводка видна
      прямо на странице прогона, без открытия логов и без прав;
    - весь каталог `target/gate-logs/latest/` выгружается артефактом при
      падении (`if: failure()`), чтобы полный вывод можно было скачать.

  Оба пункта — по три строки YAML и решают ровно ту проблему видимости,
  которая в этом репозитории уже описана как исторически дорогая.

**Связь с G-1**

  Не смешивать. Журнал приложения живёт в пользовательском каталоге и служит
  пользователю; отчёт о гейте живёт в `target/` и служит разработчику. Общего у
  них — только правило о времени и здравый смысл. Одна подсистема на два таких
  разных потребителя получится хуже обеих.

ЧЕГО В ЭТОМ РАЗДЕЛЕ НЕТ
================================================================================

  - Не выбрана окончательно библиотека: `tracing` рекомендован, но это решение
    владельца, потому что это новая производственная зависимость, а правила

    («ни один крейт не ходит в сеть») это исключает, и правильно исключает.
    Всё, что описано выше, — файлы на машине пользователя, и ничего больше.

    stdout занят протоколом, stderr — единственный свободный поток, и файл
    журнала может оказаться единственным способом что-то узнать о работе
    сервера. Стоит решить отдельно, когда G-1 будет сделан для двух остальных
    поверхностей.
