S-1. [КРИТИЧНО] Пять из шести Tauri-команд обходят проверку пути, которая
     написана специально для них — граница изоляции вебвью не держится
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Предыдущий аудит (находка №6) обнаружил, что шесть Tauri-команд принимают
  `result_path` от вебвью без всякой проверки и распаковывают по нему архивы и
  отдают файлы системному обработчику. В ответ появилась функция
  `resolve_export_result`, которая сверяет путь с фактом: в истории экспортов
  записан `result_path` каждого прогона, и путь приемлем ровно тогда, когда его
  произвёл какой-то прогон. Рассуждение в комментарии образцовое:

      // The check is against a *fact* rather than a shape … No amount of string
      // cleverness can forge that.

  Затем в `export/mod.rs` появилась пара функций: `extracted_bundle_dir` —
  «проверить и распаковать», и `extract_validated_bundle` — «распаковать то, что
  уже проверено». Комментарии на них говорят прямо:

      /// The single gate for five of the six commands that used to take this
      /// path on trust.                                   ← над extracted_bundle_dir

      /// Nothing but [`extracted_bundle_dir`] should call it.
                                                           ← над extract_validated_bundle

  **Оба утверждения неверны, и опровергаются двумя строками того же файла.**

      export/mod.rs:341   read_project_profile   → extract_validated_bundle(…)
      export/mod.rs:393   open_bundle_report     → extract_validated_bundle(…)

  `open_bundle_report` — общая реализация для `open_dashboard`,
  `open_project_overview`, `open_onboarding_guide` и `open_review_checklist`.
  Итого пять команд из шести идут мимо проверки. Через `extracted_bundle_dir`
  ходит ровно одна — `prepare_handoff` (`ai.rs:53`), и та не работает по причине
  S-2.

  То есть находка №6 предыдущего аудита закрыта на бумаге. В коде она открыта
  для тех же пяти команд, для которых была открыта тогда.

  Что именно можно сделать через эту дыру — считаем от модели угроз, которую
  проект сам себе назначил. Проект объявляет вебвью недоверенным: файловых
  разрешений у него нет вовсе, и каждая файловая операция — команда. Значит,
  сценарий «вебвью скомпрометирован» (XSS в интерфейсе, вредоносный отчёт,
  который каким-то образом попал в DOM) — это тот сценарий, ради которого
  capability-файл написан. При нём:

    - `open_dashboard(path)` с произвольным `path`:
      если это каталог — `find_in_bundle` рекурсивно ищет в нём
      `REPORT_DASHBOARD.html` и отдаёт найденное `tauri_plugin_opener::open_path`,
      то есть системному обработчику. Проверка «файл лежит внутри корня» есть,
      но корень — это тот самый путь, который прислал вебвью.
    - `read_project_profile(path)` с путём на `.zip`:
      `extract_zip_safely` распакует произвольный архив с диска в
      каталог приложения. Распаковка сама по себе безопасна (обход путей закрыт,
      бюджет есть), но это запись произвольного объёма в чужое место по команде
      недоверенной стороны.
    - `read_project_profile` возвращает содержимое `PROJECT_PROFILE.json` из
      любого архива, до которого дотянется процесс, — то есть это ещё и чтение.

  Ни одно из этого не является удалённым исполнением кода. Это ровно та потеря
  изоляции, которую capability-файл был призван предотвратить, и которую
  документация объявляет предотвращённой.

К ЧЕМУ ПРИВОДИТ
  Заявленная и задокументированная граница безопасности не существует для пяти
  из шести команд, которые она описывает. Хуже того — она *выглядит*
  существующей: есть функция, есть комментарий, есть тест. Следующий человек,
  читающий этот модуль, поверит комментарию.

КАК ИСПРАВИТЬ (senior+)
  Не «дописать вызов в двух местах» — так же можно забыть в третьем. Правило
  надо сделать невозможным нарушить, тем же способом, каким проект уже сделал
  недоступным сырое чтение файла в отчётах (`text::read_text_unredacted` плюс
  гейт-шаг `report_redaction`).

  1. **Типом.** Пусть `extract_validated_bundle` принимает не `&Path`, а
     `&ValidatedResultPath` — newtype с приватным полем, который умеет
     появляться только из `resolve_export_result`. Ровно тот приём, который
     этот же проект уже применил в CLI для `RenderedError`, и с той же
     мотивацией: «снаружи этого модуля нет способа сконструировать его иначе,
     поэтому „кто-то напечатал ошибку напрямую“ — ошибка, которую здесь нельзя
     совершить». Компилятор тогда отвергает оба нынешних обхода.

  2. Заодно убрать соблазн: `extract_validated_bundle` может стать приватным
     методом на этом newtype (`ValidatedResultPath::extract(&self)`), и тогда
     «распаковать непроверенное» — не вопрос дисциплины, а несуществующая
     операция.

  3. **Тест на класс ошибки**, а не на случай. Кроме теста «непроверенный путь
     отвергнут» нужен тест «команда, которой дали чужой путь, до распаковки не
     доходит» — по одному на каждую из шести команд, а лучше один параметризованный.
     Сейчас таких нет ни одного (см. `04-TESTS.txt`, T-1).

  4. Исправить комментарии. Оба нынешних утверждают факт, который был неверен в
     момент написания.

  Порядок: сначала S-2 (иначе после включения проверки перестанут работать все
  шесть команд, а не одна), потом это.

S-2. [КРИТИЧНО] Сама проверка отказывает всегда: запрос уходит с `LIMIT 0`,
     а SQLite на `LIMIT 0` возвращает ноль строк
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `resolve_export_result` спрашивает историю так:

      let runs = codepack_storage::list_export_runs(&connection, None, 0)?;
      let known = runs.iter().any(|run| …);
      if !known { return Err(… "is not an export this installation produced" …) }

  Третий аргумент — `limit`, и он подставляется в SQL прямо:

      … ORDER BY r.started_at DESC, r.id DESC
      LIMIT ?2

  В SQLite `LIMIT 0` означает «ноль строк». Безлимитным является `LIMIT -1`, а
  не `LIMIT 0` — и это единственное место в кодовой базе, где ноль передан в
  этот параметр. Проверено запуском (`sqlite3` in-memory, вне репозитория):

      LIMIT 0  -> []
      LIMIT -1 -> [(1,), (2,), (3,)]
      LIMIT 2  -> [(1,), (2,)]

  Следовательно `runs` всегда пуст, `known` всегда `false`, и функция **отвергает
  любой путь, включая только что произведённый этой же установкой**.

  Единственный её вызывающий — `prepare_handoff` через `extracted_bundle_dir`.
  Значит, кнопка «передать бандл агенту» на экране результата в десктопном
  приложении **не работает никогда**, с сообщением:

      «<путь> is not an export this installation produced, so it will not be opened»

  Почему это не заметили — самое поучительное в находке. Тестов на функцию три,
  и все три проверяют отказ:

      a_path_no_run_produced_is_refused                     — ожидает Err
      an_empty_or_missing_path_is_refused_before_the_database_is_touched — ожидает Err
      preparing_refuses_a_path_no_run_produced              — ожидает Err

  А четвёртый тест, который должен был проверить приёмочную ветку, её обошёл, и
  в его комментарии прямо написано, почему:

      // Through `handoff::prepare` rather than the command: since audit No. 6 the
      // command first checks that the path is an export this installation produced,
      // and a temporary directory is deliberately not one.

  То есть неудобство от неработающей проверки заметили — и обошли в тесте,
  вместо того чтобы усомниться в проверке.

К ЧЕМУ ПРИВОДИТ
  Заявленная возможность S13 «передать готовый бандл локальному агенту» в
  графическом приложении не работает вообще. В CLI она работает — там своя
  реализация `handoff`, без этой проверки, — поэтому расхождение между двумя
  фронтендами максимальное: одна и та же функция в одном месте работает, в
  другом отвечает обвинением в подлоге.

  Вторая, менее очевидная часть: после исправления S-1 (когда пять команд начнут
  ходить через проверку) этот дефект мгновенно превратится из «одна кнопка не
  работает» в «шесть кнопок не работают». Поэтому чинить надо раньше.

КАК ИСПРАВИТЬ (senior+)
  1. Немедленно и минимально — не передавать ноль. Но не подставлять `-1` и не
     заводить магическое число: сделать намерение выразимым. `list_export_runs`
     принимает `limit: usize`; правильнее принять `Option<usize>` и превратить
     `None` в `LIMIT -1` внутри запроса, где это одна строка и один комментарий.
     Тогда «все прогоны» станет тем, что оно есть, а не значением, которое надо
     угадать.

  2. Лучше того — не спрашивать историю списком вовсе. Вопрос «есть ли прогон с
     таким `result_path`» — это `SELECT EXISTS(…)`, один запрос, один булев
     ответ, без выгрузки всей истории в память и без канонизации каждого
     записанного пути в цикле (сейчас на каждый прогон делается
     `Path::canonicalize`, то есть системный вызов). При тысяче прогонов это
     тысяча обращений к диску на одно нажатие кнопки.

     Канонизацию при этом надо сохранить — она там не для красоты, а чтобы `.`,
     регистр на Windows и короткое имя 8.3 сходились. Форма: выбрать кандидатов
     по имени файла (`WHERE result_path LIKE '%' || ?1`), и канонизировать
     только их.

  3. Тест на приёмочную ветку. Это T-1 в `04-TESTS.txt`: записать прогон в
     тестовую базу и убедиться, что его `result_path` принимается. Он невозможен,
     пока команды ходят в реальную базу пользователя (T-2), — поэтому три
     находки чинятся одной задачей.

  4. Проверить остальные вызовы `list_export_runs` на тот же вопрос: их четыре,
     и все остальные передают положительные числа. Здесь всё в порядке; сказано,
     чтобы не осталось сомнения.

S-3. [ВЫСОКО] `deny.toml`: одиннадцать advisories игнорируются по причине,
     которая перестала быть правдой в тот день, когда появились Linux-пакеты
--------------------------------------------------------------------------------

ОПИСАНИЕ
  В `deny.toml` одиннадцать записей об игнорируемых предупреждениях, и у всех
  одно обоснование:

      # gtk-rs GTK3 bindings (unmaintained; GTK4 bindings exist but Tauri's tray
      # crates have not migrated) -- via tray-icon/muda -> tauri, the Linux tray
      # backend, which this Windows-only build does not even compile.

  Это было верно, пока сборка была Windows-only. С 2026-09-06 продукт собирается
  в `.deb`, `.rpm` и AppImage, и GTK3-стек не просто компилируется — он
  **поставляется пользователю внутри пакета**, а `libgtk-3-0` объявлена в
  `Depends`. Одиннадцать неподдерживаемых крейтов из этого стека теперь в
  продакшн-поставке, и решение их игнорировать основано на утверждении, которое
  сам же репозиторий опровергает соседним файлом.

  Технически ни один из этих RUSTSEC — не уязвимость: `RUSTSEC-2024-0411…0420`
  и `RUSTSEC-2024-0370` — это «unmaintained», информационные. Так что немедленной
  опасности нет. Опасен механизм: гейт-шаг `ignored advisories` существует
  специально, чтобы просроченные записи всплывали, — но он, по собственному
  комментарию, «reporting only», и проверяет он только, что запись ещё
  *совпадает* с чем-то, а не что её обоснование ещё истинно. Обоснование
  проверить автоматически нельзя; значит, его должен проверять человек, а
  человеку никто не сказал, что оно устарело.

  Это ровно тот класс дефекта, который предыдущий аудит назвал системным:
  правило записано в двух местах, одно место изменили, второе — нет.

К ЧЕМУ ПРИВОДИТ
  Сейчас — репутационно и процессно: в файле политики безопасности написана
  неправда, и она снимает вопрос, который надо было бы задать заново. Если
  завтра в одном из этих одиннадцати крейтов появится настоящая уязвимость
  (`RUSTSEC-…` с CVSS, а не «unmaintained»), запись `ignore` по имени advisory
  её не пропустит — идентификаторы разные. Но человек, читающий файл, увидит
  строку «Linux tray backend only, не компилируется» и с высокой вероятностью
  примет решение, исходя из неё.

КАК ИСПРАВИТЬ (senior+)
  1. Немедленно и без изменения поведения — переписать обоснование правдой:

        # gtk-rs GTK3 bindings (unmaintained; Tauri's tray crates have not migrated
        # to GTK4). Since 2026-09-06 this stack IS built and shipped: the .deb/.rpm/
        # AppImage carry it, and libgtk-3-0 is a declared dependency. Kept ignored
        # because all eleven are "unmaintained" advisories, not vulnerabilities, and
        # the only way off them is Tauri migrating to GTK4. Revisit: 2026-12-01.

     Дата пересмотра — не украшение: без неё запись бессрочна, а бессрочная
     запись `ignore` — это отключённая проверка.

  2. Усилить гейт-шаг: он умеет находить записи, которые перестали совпадать.
     Пусть он дополнительно требует, чтобы у каждой записи была дата
     пересмотра и чтобы она не была в прошлом. Это проверяемо автоматически,
     в отличие от текста обоснования, и оно закрывает именно этот сценарий —
     обоснование, устаревшее вместе с проектом.

  3. Отдельно проверить остальные пять записей (`unic-*` через `tauri-utils`) на
     тот же вопрос: они всегда были в сборке, их обоснование не устарело. Сказано
     для полноты — там всё в порядке.

S-4. [ВЫСОКО] CI: сторонние действия подключены по подвижным тегам, а
     `permissions` не задан — токен получает права по умолчанию
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Два независимых упущения в одном файле.

  (а) **Подвижные теги.** Все семь сторонних действий подключены так:

        actions/checkout@v5      pnpm/action-setup@v6     actions/setup-node@v6
        Swatinem/rust-cache@v2   taiki-e/install-action@v2
        actions/setup-python@v6  actions/upload-artifact@v5

      Тег в git — подвижная ссылка. Кто владеет репозиторием действия, тот в
      любой момент может перевесить `v2` на другой коммит, и следующий же прогон
      выполнит другой код — с доступом к рабочему дереву, к кэшу сборки и к
      `GITHUB_TOKEN`. Это не гипотеза: компрометации популярных действий с
      перевешиванием тегов случались, и рекомендованная GitHub защита — пинить
      по SHA коммита.

      Для проекта, чья первая строка в README — «privacy is absolute» и чей гейт
      специально читает манифесты в поисках HTTP-клиента, доверять подвижному
      тегу — несоразмерно слабое звено. Собственный код проверяется механизмом;
      чужой, исполняющийся в том же процессе, — тегом.

  (б) **Права токена.** В `ci.yml` нет блока `permissions` ни на уровне workflow,
      ни на уровне джоб. Значит, действуют настройки репозитория по умолчанию —
      а для репозиториев, созданных до изменения политики GitHub, это
      `contents: write` и далее по списку. Ни одна джоба здесь не должна
      ничего писать: гейт читает и собирает, `package-linux` загружает артефакт
      (для чего прав на содержимое не нужно).

      Комбинация (а)+(б) — это и есть цепочка: скомпрометированное действие
      получает токен с правом записи в репозиторий.

S-5. [СРЕДНЕ] При распаковке накладывается режим прав из архива без учёта umask:
     архив может попросить файл, доступный на запись всему миру
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `unix_mode::apply_extracted` рассуждает про безопасность правильно и в
  комментарии это объясняет: маска `0o777` снимает setuid/setgid/sticky, `| 0o600`
  гарантирует, что распаковавший сможет прочитать. Но остальные девять бит
  берутся из архива как есть:

      std::fs::set_permissions(path, Permissions::from_mode((mode & 0o777) | 0o600))

  Архив, в котором член записан с режимом `0o777`, распакуется в файл `rwxrwxrwx`.
  Ни `umask` процесса, ни какой-либо потолок не применяются.

  Сравнение с образцом: `tar` без `-p` (то есть по умолчанию для непривилегированного
  пользователя) накладывает umask; `unzip` делает то же. То есть привычное для
  Unix поведение — «права из архива, ограниченные моей umask», а здесь —
  «права из архива».

  Реалистичный сценарий вреда: бандл распакован в общий каталог на многопользовательской
  машине (`/tmp`, сетевой диск, CI-раннер с несколькими джобами). Внутри —
  `gradlew` или `configure` с режимом `0777`. Любой локальный пользователь может
  их переписать, а следующий, кто запустит сборку из этого бандла, исполнит чужой
  код. Это локальное повышение привилегий через артефакт, который продукт сам же
  назвал безопасным для передачи.

ФАЙЛЫ
  crates/codepack-archive/src/unix_mode.rs:49-59   (`apply_extracted`)
  crates/codepack-archive/src/unix_mode.rs:86-100  (тест на setuid — есть)
                                                   (теста на o+w — нет)

К ЧЕМУ ПРИВОДИТ
  Распакованный бандл может содержать файлы, доступные на запись посторонним.
  Продукт, чья заявленная ценность — «безопасно передать проект наружу», при
  приёме передачи ослабляет права.

КАК ИСПРАВИТЬ (senior+)
  Наложить umask, как делают штатные распаковщики. `std` не даёт прочитать umask
  без изменения (`libc::umask` — единственный способ, и он не потокобезопасен),
  поэтому есть два пути:

  (а) **Без чтения umask** — просто снять запись для группы и мира, оставив
      всё остальное:

          let mode = (mode & 0o777 & !0o022) | 0o600;

      `0o022` — умолчание umask на подавляющем большинстве систем. Это огрубление,
      но огрубление в безопасную сторону, и оно не отнимает исполняемый бит,
      ради которого весь модуль написан.

  (б) **С чтением umask** один раз при старте процесса, через `libc::umask(0)`
      + немедленное восстановление, под `OnceLock`. Точнее, но требует
      зависимости `libc` и `unsafe`, что в этом проекте — отдельное решение
      владельца.

  Рекомендуется (а): одна строка, ноль зависимостей, поведение предсказуемое.

  Тест, который должен упасть первым:
      `#[cfg(unix)]` — `apply_extracted(&f, Some(0o777))`, затем
      `assert_eq!(mode_of(&f) & 0o022, 0, "чужая запись пережила распаковку")`.
  Он ставится рядом с уже существующим тестом на setuid, который это же место
  проверяет с другой стороны.

S-6. [СРЕДНЕ] Установка не подписана ни на одной платформе, и канала доставки
     как такового нет
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Состояние на сегодня:
    - Windows: NSIS `.exe`, не подписан. README честно говорит про SmartScreen.
    - Linux: `.deb`/`.rpm` без подписи, AppImage без detached-подписи.
    - Рядом с каждым форматом — `SHA256SUMS.txt`, сгенерированный `xtask`.
    - GitHub Releases не используется: скачать нечего, надо собирать из исходников.
    - `action.yml` собирает из исходников на раннере — и объясняет, почему:
      «downloading an unsigned one would be the very thing this tool argues against».

  Эта позиция последовательна и честно задокументирована, так что находка — не
  «вы забыли», а «вот из чего складывается риск, и вот в каком порядке его
  снимать». Что именно не обеспечивается контрольной суммой:

    - Контрольная сумма лежит рядом с файлом. Кто может подменить файл, тот может
      подменить и сумму. Она защищает от повреждения при передаче, не от подмены.
    - На Windows отсутствие подписи означает SmartScreen на каждой установке, и
      пользователь приучается нажимать «всё равно запустить». Это дороже, чем
      кажется: привычка переносится на другие программы.
    - На Linux корпоративная политика (`apt` с проверкой подписи репозитория,
      `rpm --checksig`) просто не даст установить пакет.

  Требование владельца про дубль установщика в корне репозитория (см.
  `07-INSTALLER-ARTIFACT.txt`) делает этот пункт срочнее: неподписанный `.exe`,
  лежащий в git и предлагаемый к скачиванию с веб-страницы, — это ровно тот
  канал доставки, против которого README аргументирует в разделе про Action.

     файлы, собираемые на разных машинах.

  4. **macOS** — нотаризация, отдельная история этапа S14, вне этого аудита
     (сборки под macOS нет вовсе).

S-7. [СРЕДНЕ] Тесты десктопной оболочки работают с реальной базой данных и
     реальными настройками того, кто их запускает
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `AppPaths::resolve()` читает окружение — `%APPDATA%`/`$XDG_CONFIG_HOME`/`$HOME`
  — и никакого способа его переопределить нет: `AppPaths::for_root` существует,
  но используется только внутри тестов самого `codepack-core`.

  Значит, эти тесты идут в настоящий профиль пользователя:

      commands::export_result_tests::a_path_no_run_produced_is_refused
          → open_database() → AppPaths::resolve() → создаёт и мигрирует
            реальную ~/.local/share/codepack/codepack.db (или %APPDATA%\codepack\)

      commands::settings::tests::every_offered_preset_can_actually_be_applied
      commands::settings::tests::preset_lookup_is_case_insensitive_like_the_cli
          → apply_profile → читает реальный ~/.project_exporter_profiles.json

  Последствия три, по возрастанию:

  1. **Побочный эффект.** `cargo test` на чистой машине создаёт пользователю базу
     истории экспортов. Безобидно, но неожиданно, и это уже не тест, а установка.

  2. **Зависимость от машины.** Тесты профилей читают файл, который у
     разработчика может существовать и содержать что угодно. Тест, чей результат
     зависит от домашнего каталога, — не тест, а измерение.

  3. **Это и есть источник красного CI из прогона #106.** Два тестовых потока
     одновременно открыли одну реальную базу, которой ещё не было, и получили
     «table file_scan_cache already exists» на Windows и «table schema_version
     already exists» на Ubuntu. Гонку в миграциях исправили правильно и на
     совесть (см. `05-CONCURRENCY-AND-PERFORMANCE.txt`, P-3) — но саму причину,
     по которой юнит-тесты дерутся за пользовательскую базу, не тронули.

  apps/desktop/src-tauri/src/commands/mod.rs:97-107  (`open_database`)
  apps/desktop/src-tauri/src/commands/mod.rs:158-171 (тест, идущий в реальную базу)
  apps/desktop/src-tauri/src/commands/settings.rs:73 (`apply_profile` → реальный файл)

К ЧЕМУ ПРИВОДИТ
  Тесты небезопасны для окружения, нестабильны между машинами, и — что важнее
  всего — **непроверяемы в приёмочной ветке**: нельзя записать прогон в базу и
  проверить, что путь принят, потому что база не под контролем теста. Именно
  из-за этого S-2 прожил незамеченным.

КАК ИСПРАВИТЬ (senior+)
  1. Дать `AppPaths::resolve()` одно переопределение из окружения — например,
     `CODEPACK_HOME`, — которое, если задано, целиком заменяет корень
     (`AppPaths::for_root(...)`). Это полезно не только тестам: это стандартный
     способ запустить приложение с изолированным профилем, и `doctor` сможет
     его показывать.

     Важно сделать это именно так, а не через `HOME`: подмена `HOME` в тестах
     процессно-глобальна и сама по себе гонка (`std::env::set_var` в
     многопоточном тестовом бинаре — undefined behaviour в свежих редакциях).

  2. Команды, которым нужна база, должны принимать соединение или путь
     аргументом там, где это возможно, а `open_database()` оставаться тонкой
     обёрткой, вызываемой только из `#[tauri::command]`-уровня. Тогда логика
     тестируется без окружения вовсе.

  3. Тесты, которым нужен именно профиль пользователя, — переписать на явно
     переданный `AppPaths`.

  Эта задача разблокирует T-1, T-2 и приёмочные тесты для S-1/S-2. Делать её
  надо первой из тестовых.

S-8. [СРЕДНЕ] Повествовательные сообщения конвейера не проходят редакцию —
     сегодня их некуда записать, завтра будет куда
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Инвариант I3 говорит: значение найденного секрета не попадает в лог, отчёт,
  историю, базу, сообщение об ошибке или буфер обмена. Сообщения об ошибках в
  обеих оболочках через редакцию проходят, и на это есть парные тесты.

  А вот `log`-повествование конвейера — нет. Шаг копирования пишет:

      log(&format!("cannot copy {}: {source}", planned.relative_path));

  где `source` — `std::io::Error`. Шаг текстового дампа, git-отчёт, оркестратор —
  так же. Сейчас эти строки идут в канал прогресса, оттуда в stderr CLI и в
  событие для интерфейса, и на этом их жизнь заканчивается. Секрета в них, скорее
  всего, нет: `io::Error` несёт сообщение ядра и путь.

  Находка в том, что это **держится не на правиле, а на том, что писать некуда**.
  Как только появится файл лога (`06-LOGGING.txt` — прямое требование владельца),
  каждая такая строка станет тем, что I3 перечисляет первым: «лог». И тогда
  строчка вроде

      log(&format!("skipped by safety mode: {} ({})", path, decision.reason))

  или любое будущее сообщение, включающее фрагмент содержимого, окажется в файле,
  который пользователь потом приложит к обращению в поддержку.

КАК ИСПРАВИТЬ (senior+)
  Не «не забывать редактировать» — этим правилом проект уже обжигался и заменил
  его механизмом (`report_redaction` в гейте). Здесь механизм такой:

  1. Сделать редакцию частью **отправки**, а не частью каждого вызова. То есть

     обойти отправку нельзя.

     в одном месте, а не в пятидесяти.

  3. Тест на класс ошибки, а не на случай: прогнать экспорт проекта с
     подсаженным секретом в имени файла и в содержимом, собрать всё, что
     прошло через канал прогресса, и потребовать, чтобы значения секрета там не
     было. Такой тест уже есть для бандла целиком
     (`planted_secrets_never_reach_the_text_dump`); нужен его близнец для
     журнала.

S-9. [СРЕДНЕ] Распакованные бандлы кладутся в каталог настроек, а не данных —
     ровно то, ради чего база оттуда переезжала
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `extraction_dir_for` выбирает место для распаковки:

      let destination = paths.settings_dir().join("extracted").join(key);

  На Linux `settings_dir` — это `$XDG_CONFIG_HOME/codepack`, то есть `~/.config`.
  Туда кладётся распакованный бандл: весь проект пользователя, все отчёты, всё
  содержимое архива. Это могут быть сотни мегабайт.

  Пятью часами ранее (коммит 5cf5bdd) база данных переехала из этого же каталога
  в `$XDG_DATA_HOME` — и обоснование в `layout()` написано дословно про этот
  случай:

      // Left there … a multi-megabyte SQLite file with its `-wal` sibling lands in
      // the directory people put in a dotfiles repository or sync between machines.

  Аргумент целиком применим к распакованным бандлам, и к ним даже сильнее: база
  — мегабайты, бандл — сотни мегабайт, и в нём лежит исходный код пользователя.
  Человек, синхронизирующий `~/.config` между машинами или коммитящий его в
  dotfiles-репозиторий, унесёт туда чужой проект.

  Это не «забыли» — это то, что переезд был сделан для одного файла, а не для
  правила «данные лежат в data_dir». Второй потребитель нашёлся сразу.

S-11. [НИЗКО] `install-hooks` и `init --hook` пишут в чужой репозиторий; текущая

  `codepack` на машине не блокирует коммит (кроме `--strict`). Тестов
  одиннадцать, включая «оба режима запускают одну и ту же проверку».

  Замечание одно: хук пишется исполняемым скриптом в чужой репозиторий, и это
  самая «наступательная» операция во всём продукте — она меняет поведение чужого
  git. Стоит убедиться, что она не может записать за пределы `.git/hooks`
  выбранного репозитория, если `core.hooksPath` указывает наружу (а он может
  указывать куда угодно, в том числе на общий каталог). Сейчас значение
  `hooksPath` берётся как есть.

КАК ИСПРАВИТЬ (senior+)
  Один тест: репозиторий с `core.hooksPath = ../../elsewhere`, и утверждение, что
  установка либо отказывает, либо пишет строго внутрь. И, если решено писать —
  сообщить пользователю путь, куда на самом деле встал хук: общий `hooksPath`
  означает, что хук поставлен всем репозиториям сразу, и это стоит сказать вслух.


--------------------------------------------------------------------------------
S-12. [НИЗКО] `codepack-ai-api` остаётся в дереве, недоступный и несобираемый
      гейтом
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Восемьсот строк с HTTP-клиентом и хранилищем ключей лежат в репозитории,
  исключённые из workspace. Решение (Q41) обосновано и записано: так `ureq` и
  `keyring` не попадают ни в один бинарь, ни в `Cargo.lock`, ни в граф
  `cargo deny`. Гейт-шаг сети специально отказывается пускать члена, который на
  этот крейт сошлётся.

  Оставшийся риск невелик, но он есть: код не собирается гейтом
  (`cargo xtask ai-api` — по требованию), значит, он гниёт. Через полгода
  «включить S13» будет означать не «дописать интерфейс», а «починить восемьсот
  строк, которые полгода не компилировались». Это уже названо в `overview.md`
  как известный долг — здесь фиксируется только цена и предлагается страховка.

КАК ИСПРАВИТЬ (senior+)
  Собирать его не в гейте, а по расписанию: еженедельная джоба, запускающая
  `cargo xtask ai-api`. Она не удлиняет ни один push и ловит гниение в течение
  недели, а не через полгода. Пять строк YAML.


================================================================================
ЧТО ПРОВЕРЕНО ПО БЕЗОПАСНОСТИ И ОКАЗАЛОСЬ В ПОРЯДКЕ
================================================================================

  - Инъекция в `action.yml` закрыта: шесть входов идут через `env:`, ни одного
    `${{ }}` внутри `run:`, и в комментарии объяснено, почему выражение
    раскрывается до старта оболочки.
  - Обход путей при распаковке: `safe_member_target` принимает только
    `Component::Normal`, отказывает на первом же плохом члене; имена томов
    набора теперь проходят ту же проверку; бюджет распаковки общий на весь
    набор; есть потолки на число томов, число членов, байты и глубину.
  - `codepack_core::safe_join` отказывает сегменту с обратным слэшем ради
    одинакового ответа на всех платформах — с записанным рассуждением о том,
    что «угадать, что имел в виду windows-путь» есть способ получить второе,
    более слабое прочтение собственной проверки.
  - Изоляция сети: гейт читает каждый манифест, понимает инлайновую, табличную
    и платформенно-специфичную формы объявления зависимости, и отдельно
    отказывает члену, зависящему от исключённого крейта. Исключений внутри
    workspace нет вовсе.
  - Capability-файл вебвью минимален: `core:default`, два `dialog:*`, два
    `opener:*`. Ни файловых, ни shell-, ни HTTP-разрешений.
  - CSP не допускает удалённых источников; `devCsp` отличается от боевого
    только тем, что нужно Vite.
  - Фронтенд не содержит `{@html}`, `innerHTML`, `eval`, `localStorage`,
    `any`, `@ts-ignore`. Буфер обмена — через DOM API, а не через плагин,
    и в комментарии объяснено, что расширение capability ради удобства было бы
    решением по безопасности, а не по удобству.
  - Сообщения об ошибках проходят редакцию в обеих оболочках, и в CLI выбран
    более узкий редактор с записанным объяснением, почему широкий превращал
    «pass --hook» в «<REDACTED>».
  - SQL параметризован везде; миграции пронумерованы, транзакционны, повторный
    прогон — no-op; `foreign_keys`, `journal_mode` и `busy_timeout` применяются
    на каждое соединение.
  - `codepack scan` принудительно ставит `safe_mode=full` и `diff=all`, то есть
    отвечает на вопрос «есть ли секрет в проекте», а не «чист ли бандл».
  - `codepack-sanitize` переиспользует фильтр безопасности и редакцию, а не
    заводит второй путь наружу; формат-инструменты запускаются с argv-списком,
    без оболочки.
  - Дев-скрипты: `shell=True` не используется нигде; `clean-project` — dry-run
    по умолчанию, с отдельным модулем защищённых путей и тестами на него.
