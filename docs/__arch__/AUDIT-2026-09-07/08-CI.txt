Прогон #106 — «table schema_version already exists» / «table file_scan_cache
already exists», на ubuntu и windows, macos зелёный
--------------------------------------------------------------------------------

ЧТО БЫЛО
  Упал `commands::export_result_tests::a_path_no_run_produced_is_refused`,
  причём на двух ОС с **разными** именами таблиц. Диагноз в сообщении коммита
  d406184 поставлен точно и заслуживает цитаты как образец:

      «CI on `main` failed the release on ubuntu and windows while macos passed,
       which reads like a platform difference. The annotation carried the panic
       text and it was not one … Different tables mean a race.»

  Причина: `migrate` читал версию схемы вне транзакции, а
  `Connection::transaction` в rusqlite — DEFERRED, то есть берёт блокировку
  записи на первой записи, а не в начале. Два соединения на новой базе читали
  версию 0, оба выполняли `CREATE TABLE`, проигравший падал.

ЧТО СДЕЛАНО
  Версия читается внутри `TransactionBehavior::Immediate`; дешёвое чтение без
  блокировки перед циклом сохраняет быстрый путь. Под этим вскрылась вторая
  гонка — `PRAGMA journal_mode = WAL` не идёт через busy-handler, поэтому
  `busy_timeout` его не покрывал, — закрыта повторным чтением режима и
  ожиданием, а `busy_timeout` ставится первым. Регрессионный тест на барьере,
  с несуществующей базой. Двадцать прогонов подряд без падений.

  Исправление правильное. Подробный разбор — `05-CONCURRENCY-AND-PERFORMANCE.txt`,
  P-3.

ЧТО ОСТАЛОСЬ
  Исправлена гонка. Не исправлено то, **почему два юнит-теста вообще открывают
  одну и ту же базу**: `AppPaths::resolve()` читает окружение и не
  переопределяется, поэтому тесты десктопной оболочки идут в настоящий профиль
  того, кто их запускает (S-7 в `02-SECURITY.txt`, T-2 в `04-TESTS.txt`).

  Пока это так:
    - тесты остаются взаимозависимыми через глобальный ресурс;
    - тест на приёмочную ветку (T-1) написать нельзя, потому что база не под
      контролем теста, — и именно из-за этого критичная находка S-2 (`LIMIT 0`)
      прожила незамеченной;
    - `cargo test` создаёт пользователю базу истории как побочный эффект.

  То есть красный CI указывал на два дефекта, а исправлен один — правда, тот,
  который важнее.

C-1. [ВЫСОКО] Проверка `.deb` может ложно сообщить об отсутствующей
     зависимости: `grep -q` рвёт трубу, а `pipefail` считает это провалом
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Шаг `Inspect the .deb` начинается с `set -euo pipefail` и содержит четыре
  конвейера вида:

      if ! dpkg-deb --field "$deb" Depends | grep -q "$dependency"; then …
      if ! dpkg-deb --contents "$deb" | grep -q 'applications/.*\.desktop'; then …

  `grep -q` завершается **сразу после первого совпадения**. Пишущая сторона
  трубы закрывается, `dpkg-deb` (внутри которого работает `tar`) получает
  SIGPIPE или `EPIPE` на следующей записи и завершается с ненулевым кодом.
  Именно это и видно в логе прогона #109:

      tar: stdout: write error
      dpkg-deb: error: tar subprocess returned error exit status 2

  Дальше вступает `pipefail`: код конвейера — это код **последней ненулевой**
  команды, а не последней команды. `grep -q` вернул 0 (нашёл), `dpkg-deb` вернул
  2 (труба закрыта) → конвейер возвращает 2 → `! конвейер` истинно → проверка
  печатает:

      ::error title=deb::Depends is missing libwebkit2gtk-4.1-0

  **при том, что зависимость на месте**. То есть проверка падает тем чаще, чем
  раньше в выводе находится искомое.

  Почему в #109 этого не случилось с зависимостями: `dpkg-deb --field … Depends`
  выводит одну короткую строку, она целиком помещается в буфер трубы, записи
  после закрытия нет. А `--contents` выводит два с лишним десятка строк, и там
  это уже случилось — сообщение в логе стоит ровно между выводом contents и
  ошибкой про иконку.

  Иконочная проверка после 96555e1 безопасна: `grep -o | sort -u | xargs`
  дочитывает поток до конца. А четыре `grep -q` остались.

ФАЙЛЫ
  .github/workflows/ci.yml, шаг «Inspect the .deb» (цикл по зависимостям и
  проверка desktop-файла)

К ЧЕМУ ПРИВОДИТ
  Красная упаковочная джоба с сообщением, которое указывает не туда. Разбор
  такого падения — это несколько прогонов и час времени, потому что первое, что
  делает человек, — идёт проверять `tauri.conf.json`, где всё правильно.
  Хуже: если это случится один раз и «само пройдёт» на следующем прогоне,
  проверку начнут считать флаки и перестанут ей верить.

КАК ИСПРАВИТЬ (senior+)
  Не убирать `pipefail` — он полезен. Дочитывать поток. Самый простой вид:
  один раз положить вывод в переменную, дальше искать в ней:

      depends="$(dpkg-deb --field "$deb" Depends)"
      contents="$(dpkg-deb --contents "$deb")"

      for dependency in libwebkit2gtk-4.1-0 libgtk-3-0 xdg-utils; do
        case "$depends" in
          *"$dependency"*) ;;
          *) echo "::error title=deb::Depends is missing $dependency" >&2; fail=1 ;;
        esac
      done

      case "$contents" in
        *applications/*.desktop*) ;;
        *) echo "::error title=deb::no desktop entry in the package" >&2; fail=1 ;;
      esac

  Заодно исчезает `grep` из проверки вовсе, а `case` не имеет проблемы с
  префиксами, из-за которой в иконочной проверке пришлось объяснять, почему не
  регулярное выражение.

  Правило, которое стоит записать рядом одной строкой: **под `pipefail` левая
  часть конвейера должна дочитываться до конца**, иначе `grep -q`, `head` и
  `read` превращают успех в провал.

C-5. [СРЕДНЕ] Тест печатает в лог гейта тысячи строк сгенерированных скриптов
--------------------------------------------------------------------------------

ОПИСАНИЕ
  В логе каждого прогона `gate` — по нескольку тысяч строк bash-, zsh-, fish-,
  PowerShell- и elvish-скриптов автодополнения, вперемешку со строками
  `test … ok`. В приложенных владельцем логах они занимают заметно больше места,
  чем всё остальное вместе взятое.

  Источник:

      #[test]
      fn every_supported_shell_generates_without_panicking() {
          for shell in [Bash, Zsh, Fish, PowerShell, Elvish] {
              let outcome = run(&CompletionsArgs { shell });   // пишет в stdout
              assert_eq!(outcome, Outcome::Success);
          }
      }

  `run` генерирует скрипт прямо в `std::io::stdout()`, потому что это её работа
  как команды. Тест вызывает её как есть, и весь вывод попадает в лог.

  Два следствия:
  1. **Лог гейта нечитаем.** Это не эстетика: секция `tests` в xtask
     специально захватывает вывод, чтобы вытащить имена упавших тестов, — то
     есть все эти тысячи строк ещё и держатся в памяти строкой и потом
     печатаются целиком.
  2. **Тест почти ничего не проверяет.** Он утверждает только «не паникнуло».
     Пустой скрипт, обрезанный скрипт, скрипт для не той команды — всё пройдёт.

КАК ИСПРАВИТЬ (senior+)
  Разделить команду и генерацию:

      pub(crate) fn write_completions(shell: Shell, out: &mut dyn std::io::Write) { … }
      pub(crate) fn run(args: &CompletionsArgs) -> Outcome {
          write_completions(args.shell, &mut std::io::stdout());
          Outcome::Success
      }

  Тест пишет в `Vec<u8>` и наконец что-то утверждает: скрипт непустой, содержит
  имя команды `codepack`, содержит хотя бы одну из подкоманд (например
  `sanitize`) — то есть что сгенерировано именно это дерево команд, а не пустой
  каркас. Лог гейта при этом худеет на несколько тысяч строк.

  Это же снимает и вторую половину: сегодня, если `clap` однажды начнёт
  генерировать пустой файл, тест останется зелёным.

C-6. [НИЗКО] Джоба упаковки собирает release-сборку всего десктопа на каждый push
--------------------------------------------------------------------------------

  `package-linux` не ограничена ни ветками, ни путями: она идёт на каждый push
  в любую ветку и на каждый PR. По логу прогона #109 — 7 минут 14 секунд, из
  них 6:28 на `cargo xtask package`.

  Комментарий в workflow объясняет, почему упаковка вынесена из гейта («needs a
  release build of the whole desktop app, which would roughly double the gate's
  wall clock on every push for a check that only has to hold when packaging
  changes»). Рассуждение верное — и ровно оно требует следующего шага, который
  не сделан: раз проверка нужна, «только когда меняется упаковка», пусть она
  тогда и запускается.

      on:
        push:
          paths:
            - 'apps/desktop/src-tauri/tauri.conf.json'
            - 'apps/desktop/src-tauri/linux/**'
            - 'crates/xtask/src/frontend.rs'
            - '.github/workflows/ci.yml'

  плюс `workflow_dispatch` и безусловный запуск на теге. Экономия — семь минут
  раннера на каждый push, который упаковки не касается, то есть на почти каждый.

--------------------------------------------------------------------------------
C-8. [НИЗКО] `Swatinem/rust-cache` кэширует три ОС, но `package-linux` строит
     release, а `gate` — debug: кэш между ними не переиспользуется
--------------------------------------------------------------------------------

  Обе джобы используют `Swatinem/rust-cache@v2` без ключей, то есть каждая
  ведёт свой кэш. Это правильно (профили разные), но стоит заметить: полная
  release-сборка десктопа с нуля — самая дорогая операция в конвейере, и она
  повторяется целиком, если кэш вытеснился (у GitHub 10 ГБ на репозиторий, и
  три ОС × два профиля их выбирают быстро).

  Дешёвое улучшение: дать `package-linux` явный `prefix-key`, чтобы её кэш не
  соревновался с кэшем гейта той же ОС, и `save-if: github.ref == 'refs/heads/main'`,
  чтобы ветки кэш только читали, а не заполняли его своими вариантами.

ЧТО ПРОВЕРЕНО ПО CI И ОКАЗАЛОСЬ В ПОРЯДКЕ
================================================================================

  - **Матрица из трёх ОС восстановлена и `fail-fast: false`** — то есть зелёная
    Windows-нога больше не прячет красную Unix. Решение записано вместе с
    причиной (история Q21), и оно уже окупилось: прогон #111 нашёл дефект за
    один круг.
  - **Аннотации.** Гейт называет упавшую секцию, а секция `tests` — каждый
    упавший тест по имени и с текстом паники. Рассуждение записано и оно
    точное: лог шага требует прав администратора на репозиторий, аннотация —
    нет, и этот разрыв полгода держал Q21 нераскрытым. Экранирование `%`, CR и
    LF сделано, длина клипуется, и на всё это есть тесты.
  - **`--no-fail-fast`** — чтобы красный прогон называл все упавшие тесты сразу,
    а не по одному крейту за круг. Обоснование записано.
  - **Frontend-проверки падают, а не пропускаются, когда `CI` установлен.**
    Это ровно тот случай, где молчаливый пропуск был бы дырой, и он закрыт
    механизмом, а не дисциплиной: удалить шаг `pnpm install` из workflow теперь
    нельзя тихо.
  - **То же для набора тестов `scripts/`** — с тем же обоснованием: он охраняет
    инструмент, который удаляет файлы, и «не запускается нигде» для него не
    вариант.
  - **Приёмочный шаг S10** гоняет настоящий headless-экспорт release-сборкой на
    всех трёх ОС, и обрабатывает код возврата 3 осознанно (собственные фикстуры
    проекта содержат учётные данные намеренно), с объяснением, почему
    `|| exported=$?`, а не голый вызов с последующим `$?`.
  - **Контракт кодов возврата проверяется отдельным шагом** на настоящей
    фикстуре: 3 для проекта с учётными данными, 1 для отсутствующего проекта.
  - **Проверка `.deb` читает то, что бундлер реально записал**, а не доверяет
    конфигурации: control-файл, список файлов, зависимости, desktop-entry,
    иконки. Это правильная форма проверки упаковки.
  - **Контрольные суммы проверяются в CI** (`sha256sum -c`) в каталоге каждого
    формата — то есть проверяется и сам факт, что файл читается из того
    каталога, где лежит.
  - **`concurrency` с `cancel-in-progress`** и общей группой для ветки и её PR —
    без этого включение push на все ветки удваивало бы матрицу.
  - **Системные зависимости Linux** перечислены явно и с объяснением, почему
    `libdbus-1-dev` остаётся после ухода `keyring`: «GTK pulls D-Bus in
    regardless, and dropping a package on the strength of an untested guess is
    how a green build becomes a red one on somebody else's machine».
  - **Rust-тулчейн закреплён** `rust-toolchain.toml` и подтягивается через
    `rustup show`, а не «что стоит на раннере».
  - **`cargo-deny` ставится через `taiki-e/install-action`**, а не собирается
    из исходников на каждом прогоне.
